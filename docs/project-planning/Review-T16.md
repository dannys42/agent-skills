## Important

One more qualifies (the `g3` eval regressions, on low-confidence evidence); it opens the notable tier.

**1. The milestone skill keeps a name that says it plans one rung** (roadmap-plan-next-rung, the whole skill; the rename is proposed in the commit message of its rewrite). The skill now plans a whole milestone, reviews escalated fold-backs and closes milestones. Nothing in it plans a single rung any more, yet its name and its trigger phrase "plan the next rung" still say so. The owner never types it (`/rung` dispatches it), so the name mostly guides an agent choosing a skill and anyone reading the metrics log.
Why: a name others build on: links from four skills, the `skill` stamp on every step event, the dispatch targets `roadmap next` prints, and the install lists. A rename ruling becomes its own structure-only task.
- **`milestone`** (proposed first, recommended). E.g. `/rung` dispatches `milestone plan M2`, and step events read `milestone 0.12.0`. Pro: short, and covers all three procedures. Con: the same word as the domain term, so "the milestone skill" and "the milestone" can blur in prose.
- **`plan-milestone`** (proposed second). Pro: a verb phrase like the other skills, with no clash with the term. Con: says nothing of the escalation review or close, the same mismatch in a smaller form.
- **Keep `roadmap-plan-next-rung`.** Pro: no link, stamp or test changes, and the metrics history stays under one name. Con: the name and triggers advertise per-rung planning, which the cadence retired, so an agent may pick it to plan one rung.

**2. Waiting state for the owner lives in git-ignored scratch notes** (roadmap-plan-next-rung `references/handoff.md`, "Where" and "Consume"; `roadmap next` routing). Every stop that waits on the owner writes a note such as `<DocDir>/Handoff/escalation-L3.md` when the fold-back of L3 (import orders) escalates. The first write creates `Handoff/.gitignore` holding `*`, so no note is ever committed. The newest live note outranks the roadmap in `roadmap next`; a note whose waiting point is gone is skipped, and `metrics signals` warns about one older than 14 days.
Why: a file format three skills and the tool read, and it decides whether a wait survives a move to another machine or worktree.
To settle it: do you ever resume a project on another machine, or in a fresh worktree, while a step waits on you?
- **A self-ignoring folder in the doc directory** (as written, recommended). Pro: no edit to the project's `.gitignore`, no setup in any clone, and the committed markers (item 3) still route without the note. Con: a note does not travel; a new clone or worktree loses its "Done, Pending, Decided" and the resume works from the roadmap lines alone.
- **Commit the notes**, deleted by the step that consumes them. Pro: the wait survives a clone and shows in history. Con: a commit for each wait, and half-applied rulings ("Decided") land in git.
- **Outside the repository**, under `~/.local/state/danny-agent-skills/handoff/<project>/`. Pro: nothing in the working tree. Con: tied to one machine, harder to find by hand, and the tool must map a project to its folder.

**3. Where a rung or a close stands is written as lines the tool parses** (auto-fold-back.md, steps 3 and 4; roadmap-plan-next-rung, "Milestone planning" step 6 and "Milestone close"; tasklist-run, step 6). Starting a rung commits `Base: <sha>` under the brief's `Status:` line (with no brief, in the tasklist's `Source:` line). An escalated fold-back adds an `Escalation: <date>` block under the rung, one bullet per difference. A close records each finished step under the milestone as `Close: checks passed`, `tidy run`, `re-read <sha>`, `awaiting demo` and so on. And a closed rung list still in the doc directory, not moved to `Completed/`, means the fold-back did not finish. E.g. after the fold-back of L3 (import orders) escalates, `roadmap next` returns `escalation` until the review deletes the block.
Why: stored format in every roadmap and brief, parsed by the tool; changing it later means migrating projects.
- **Lines in the files they describe** (as written). Pro: readable by hand, committed, survives any session or clone, and `rung`'s hand-made fallback can follow it. Con: four signals in three places (brief, rung section, milestone line, where a list sits), and today nothing catches one left behind. `roadmap lint` (`lintMilestones` in `Milestones.swift`) warns only about an `in progress` rung or an `Escalation:` marker on a rung outside the current milestone. A left-over `Escalation:` on a done rung of the current milestone misroutes: `roadmap next` matches any rung carrying the marker, whatever its status, and routes an Opus escalation review until the line is deleted. A left-over `Close:` on a done milestone does not misroute (routing reads it only for the current milestone's `why` text), but it stays in `Map.md`.
- **As written, plus a lint check** (recommended): `roadmap lint` flags an `Escalation:` on a rung that is not `in progress` and a `Close:` on a milestone that is not `current`, and routing ignores an `Escalation:` on a done rung. Pro: keeps the readable lines and removes the one misroute. Con: a small tool change and two more lint rules.
- **One state file per project** (e.g. `<DocDir>/State.md` holding rung, base and step). Pro: one place to read and lint. Con: repeats statuses the roadmap already holds, so the two can disagree, and it is a new format for the tool.

**4. `/rung` decides per step whether an Opus step runs as a subagent or needs a new session** (rung SKILL.md, "Model and where it runs"; roadmap-plan-next-rung, "Escalation review" and "Milestone close" step 3). Owner-facing steps (milestone planning, the demo, a re-plan, design) always need a session on the right model. Non-interactive steps (the escalation review's reading and judging, the close's re-read of every fold-back) may run as an Opus subagent briefed by the handoff note when the context is small, and the agent says its choice in one line, e.g. `Escalation review: non-interactive, small context → Opus subagent.` So a Sonnet session that finishes L3 (import orders) and sees its fold-back escalate can have the review done without the owner switching models, unless the review returns items needing an Opus conversation.
Why: changes the model per step and how often the owner switches sessions.
To settle it: the open task on whether `tasklist-run` pauses itself for a fresh session (Tasklist-Redesign.md) touches the same choice; the first milestone's metrics then show what each mode costs.
- **The agent picks per step and says why** (as written, recommended). Pro: fewer session switches where the context is small. Con: rests on the agent's guess of context size, so the same step can cost differently on two runs, which blurs the metrics.
- **Always a new session for an Opus step.** Pro: predictable, and every Opus step is logged the same way. Con: a switch for each escalation, even a one-line drift.
- **Always a subagent for a non-interactive step.** Pro: predictable and cheapest in owner time. Con: a large re-read in a subagent can lose detail in its report back.

**5. Milestone close can stop up to three times, not once** (roadmap-plan-next-rung, "Milestone close" steps 1, 2 and 4). The spec pauses the close at the demo. The skill also ends the session when the full suite fails (a fixes list runs on Sonnet, then close resumes) and when the owner chooses to run the tidy (it runs in its own Sonnet session, then close resumes at the re-read). Worst case for M1 (data in one place): checks fail, Sonnet fixes, Opus close resumes and offers the tidy, Sonnet tidies, Opus re-reads and demos, the owner rules later, Opus applies the ruling, retro and re-plan: four Opus sessions.
Why: the owner's session count, and the Opus cost per milestone that the cadence set out to cut.
- **As written** (recommended). Pro: the re-read and the demo see the final code, so nothing fixed or tidied after the demo goes unreviewed. Con: in the worst case several session switches per close.
- **Tidy after the ruling**, as the first list of the next milestone. Pro: one pause fewer, and the tidy never interrupts a close. Con: tidied code is first re-read at the next close, a milestone later.
- **Fixes and tidy as Sonnet subagents inside the close session.** Pro: no switch for either. Con: a long Opus session carrying both, the cost the cadence moved off Opus.

## Notable

**6. The `g3` evals regressed on two graders, both on noisy verdicts** (Design-Blueprint_And_Milestones.md, "Eval results" and "g3 findings"). After this work, foundation-before-goal rose to 0.93 and over-detail-trap's milestone-scope rose from 0/3 to 2/3, but over-detail-trap's design-depth fell from 1/3 to 0/3 and its summary-names-ids from 3/3 to 1/3. Read by hand, one summary-names-ids failure is a confirmed judge error (likely 2/3), and one design-depth failure looks wrong (unconfirmed); the real failures are a summary naming D9 (keeping milestone 1 to the domain method) and M2 (the second milestone) with no names, and a design sketching the second milestone's detail. The new demo-stop-handoff case scores 0.79, understated: its handoff-ignored grader can never pass (`max: 0` with `min` defaulting to 1; a fix task is open), and stop-message passed 1/3 (one run missed the exact `Next:` line, one likely labelled the re-read's items with bare IDs).
- **Accept the work; fix the grader and re-score** (recommended). Pro: the drops sit inside n=3 noise, and re-scoring shows whether stop-message's bare IDs are real. Con: the two real failures wait for a later eval to show whether they recur.
- **Re-run over-detail-trap before closing this review** (about $4.41). Pro: tells noise from a real drop. Con: cost and time for a result that is still noisy at n=3.
- **Add a fix task now** for bare IDs in closing summaries and in the re-read's items. Pro: targets the one failure seen in two cases. Con: may tighten text for what is partly judge noise.

**7. Planning outranks every other step whenever a current-milestone rung has no tasklist** (roadmap-plan-next-rung, "Milestone planning"; `NextStep+Milestones.swift`). If an owner request mid-milestone adds L6 (export to CSV) while L4 (folder suggestions) has open tasks, the next `/rung` asks for an Opus planning session for L6 before L4's run continues.
- **Plan first** (as written, recommended). Pro: a new rung that changes a seam L4 uses is designed before L4 is built on the old one, and close can never start with an unplanned rung. Con: an Opus session interrupts a Sonnet run.
- **Finish the in-progress rung, then plan.** Pro: no switch mid-rung. Con: a seam change reaches L4 only after it is built, and the route needs one more condition.

**8. A rung with no open decisions gets no brief** (roadmap-plan-next-rung, "Milestone planning" step 5; auto-fold-back.md, inputs). Its tasklist's `Source:` cites the design doc, its `Base:` goes in that line, and the fold-back compares against the design rows alone. E.g. L5 (more file types), a breadth rung repeating a proven shape.
- **No brief** (as written, recommended). Pro: no page restating seams for an obvious rung. Con: two shapes of fold-back input, and nowhere to put the "As built" lines.
- **Always a brief, a few lines when thin.** Pro: one shape for every rung; `Base:` and "As built" always in the same place. Con: briefs that only repeat citations.

**9. `Map.md` is generated after the commits, and not at all after a fold-back** (roadmap-plan-next-rung, "Milestone planning" step 6 and "Milestone close" step 8; auto-fold-back.md, step 4; risk-first-roadmap, "Reading"). Planning and close commit first, then run `roadmap map`, so `Map.md` is left uncommitted or is swept into a later commit; no text says whether it is tracked. The fold-back sets a rung done without regenerating it, so the owner's map shows L3 (import orders) in progress until the next re-plan, planning session or close. The escalation review's step 4 also sets a rung done without regenerating the map.
- **Generate before every commit that changes a status, and commit it** (recommended). E.g. the `Fold back rung L3` commit includes `Map.md`. Pro: the big-picture view is current in git and on GitHub. Con: a generated file in every planning, fold-back and close diff.
- **Git-ignore `Map.md` and regenerate it on demand** (`/rung status` runs the map command). Pro: never stale, no diff noise. Con: not visible on GitHub or in a clone without the tool.
- **As written.** Pro: no change. Con: stale between closes, and of unclear tracked status.

**10. A rejected demo starts the close over** (roadmap-plan-next-rung, "Milestone close" step 5). The `Close:` line is removed, the re-plan adds rungs to close the gap, they are planned and run, and close then reruns the checks, the tidy offer and the re-read of every fold-back in the milestone.
- **Start over** (as written, recommended). Pro: the second demo rests on a fresh re-read of the whole milestone. Con: a second Opus re-read of fold-backs already re-read.
- **Re-read only the new rungs, then demo.** Pro: cheaper. Con: one more `Close:` state to track, and a new rung's effect on the earlier ones is missed until the next close.

**11. A rung whose lists all moved to `Completed/` but is not done goes to an Opus escalation review** (roadmap-plan-next-rung, "Escalation review"; `NextStep+Milestones.swift`; rung's fallback table). This happens when a fold-back committed but did not set the rung done; there is no escalation marker.
- **Opus escalation review** (as written, recommended). Pro: one route, and Opus checks whether anything else was skipped; the case should be rare. Con: an Opus step for what is usually one missed status edit.
- **Re-enter the automatic fold-back on the run model.** Pro: cheap. Con: the list has already moved, so Sonnet must work out from the commit what was applied, and a real miss is judged by the model that made it.

**12. An escalation review fixes a design doc on its own when the code is right and the doc was a guess** (roadmap-plan-next-rung, "Escalation review" step 2). The review, possibly an Opus subagent, commits doc fixes and drift tasks before the owner sees anything. Only a change to a `settled` item or a decision, retiring a risk on a partial answer, or calling the rung failed comes to the owner; the stop message says what moved.
- **As written** (recommended). Pro: the owner reads only what changes agreed ground. Con: a `working` row the owner cared about can change with one line in the summary.
- **List every applied fix as a small item to veto.** Pro: nothing changes unseen. Con: more owner reading for every escalation.

**13. A milestone with a deferred or horizon rung left needs an Opus re-plan before it can close** (risk-first-roadmap, "Re-plan", the bullet "With no rung `planned`"; `decide()` in `NextStep+Milestones.swift`). When every planned rung of M1 (data in one place) is done but L7 (CSV import) waits as `deferred`, `roadmap next` routes `replan` (Opus), which must bring it back, detail it or drop it; only then does close start. The spec's Cadence table ("Re-plan inside a milestone") has no such trigger.
- **Close only after a re-plan** (as written, recommended). Pro: every leftover gets an explicit ruling before the demo, and the exit criteria are judged against a settled ladder. Con: an extra Opus session per milestone that ends with leftovers, outside the spec's trigger list.
- **Let close list the leftovers**: close shows each deferred or horizon rung beside the demo, and the owner keeps, moves or drops it in the same ruling. Pro: no extra session; the spec's trigger list stands. Con: close's ruling grows, and a leftover that should block the outcome is found only at the demo.

**14. Every re-plan runs on Opus, even one that only re-orders** (`NextStep+Milestones.swift`, the `opus` route set; rung SKILL.md, dispatch table). The spec's "Model choice" lists mid-milestone re-plans that only re-order under its Sonnet hypothesis, to be tested in the pilot, so it is not settled. E.g. a rung that answered a different question moves L5 (more file types) ahead of L4 (folder suggestions): today an Opus session.
- **Always Opus** (as written, recommended until the pilot measures it). Pro: the route need not judge in advance whether a re-plan is only a re-order, which it cannot see. Con: Opus cost for a few line moves.
- **Sonnet when the re-plan only re-orders**, Opus once it adds, reshapes or drops rungs. Pro: follows the spec's hypothesis and cuts cost. Con: the step must switch model mid-way when a re-order turns into a reshape, and the tool cannot tell the two apart from files.

## Small

**15. `roadmap name` with an unknown ID** (`RoadmapTool.swift`, `Name`) prints the known IDs with their names and exits 1. **As written** (recommended). Pro: a typo is caught. Con: a caller that reads only the exit code loses good output. **Exit 0, print `L9 (unknown)`.** Pro: never fails a pipeline. Con: a typo passes silently.

**16. A malformed `skill` stamp in the metrics log** (`metrics`, stamp check) is warned about, not rejected. **Warn** (recommended). Pro: a run never loses its log line. Con: the bad stamp stays in the log. **Reject the line.** Pro: a clean log. Con: the step's data is lost.

**17. Provisional markers are counted in tracked non-Markdown files only, in the strict form** (`Signals.swift`; `PROVISIONAL(<RungId>): replace at <MilestoneId>`), and the overdue check is skipped when the repository holds more than one roadmap. **As written** (recommended). Pro: docs that describe the marker do not count. Con: a loose marker (`PROVISIONAL: fix later`) is not counted. **Count any `PROVISIONAL(`.** Pro: nothing slips. Con: false hits from the docs and skills themselves.

**18. A handoff note is "left over" after 14 days** (handoff.md, "Consume"; `metrics signals`). **14 days** (recommended). Pro: matches "the owner replies days later". Con: a two-week holiday triggers the warning. **30 days.** Pro: fewer warnings. Con: a forgotten wait hides a month.

**19. A run's handoff note is named after its tasklist, whatever the route** (handoff.md, "Where"), e.g. `Handoff/Tasklist-L3-Import_Orders.md`, so a `user` stop and a later blocked stop on the same list overwrite one note. **As written** (recommended). Pro: one note per list, found by `tasklist-run` by name. Con: the file name does not say the route. **`<Route>-<Target>.md` for every note.** Pro: one naming rule. Con: two notes for one list when the route changes.

**20. The `accepted` count on a planning step event means accepted unchanged** (roadmap-plan-next-rung, "Milestone planning" step 6), beside `proposed`, `edited` and `rejected`. **As written** (recommended). Pro: the retro reads the unchanged share directly. Con: the name reads as "all accepted". **Rename the field `unchanged`.** Pro: says what it counts. Con: a field rename in the metrics schema and tool.
